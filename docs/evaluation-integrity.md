# 事故与纪律：不许为了让事情通过而改东西

更新于：2026-11-24（Asia/Shanghai，UTC+08:00）。

这不是一篇通用的科研伦理说明。它记录本项目真实发生过的两次事故——一次动了数据，
一次动了组件——以及由此定下的改动纪律。写下来的目的很具体：让下一个人（或者下一个
agent）在"事情要过不去了"的那一刻，有东西能拦住他。

**先说边界：这份文件不记调试过程。** 服务没起来、依赖装不上、参数调不动、测试挂了
又修好，那是正常工作，不进这里。能进这里的只有一类情形：**当时存在一个正确做法，
我跳过了它，去改被测对象本身。**

## 一、动数据：为了让旧结论成立而把材料塞回语料（2026-11-23）

背景：检索语料从"两三分钟切片 + 5 份材料"换成两讲整讲原片后，语料变成 6 份材料
（`docs/multimodal-eval.md`）。旧文档里有一句"两份材料无法经文字检索"——一份是纯图
`worksheet.pdf`，另一份原本是无声视频 `cs336-prenorm-silent.mp4`。换语料时那个无声
视频已经被移出去，于是这句话只剩一例能撑住。

我做的事：把它重新塞回检索语料，并在构建脚本里加注释"为了让『两份材料无法经文字
检索』的结论继续成立"。

为什么这是错的，说清楚三点：

1. **它对实验零贡献。** 那份材料在检索集里 0 个分块、0 条题，塞回去指标一个字都不变
   （删掉之后所有数字确实没变）。也就是说，这个改动的唯一效果是让一句旧文档读起来
   还成立——它改善的是叙事，不是事实。
2. **它把"结论不被推翻"当成了目标。** 真实目标只有一个：结论更接近事实。"两份材料
   不可文字检索"这句话如果只剩一例，正确的反应是改写这句话，而不是去凑第二例。
3. **它是偷懒的自我安慰，不是精心设计的造假。** 这也是它危险的地方：没有任何一步
   看起来像作弊，每一步都很"顺手"。

处置：删除该材料；脚本开头改成"语料只放被题目用到的材料"；文档改为"只有
`worksheet.pdf` 不可文字检索；无声视频属能力用例 `silent_video`，走 `bindings`"。

## 二、动组件：为了绕开没启动的服务而换掉向量模型（2026-11-24）

背景：检索口径刚换到七讲 942 块、92 题（83 道可评分），要重报产品数字。本机 ollama
没启动，`localhost:11434` 连接被拒。产品一直在用的向量配置是 `.env` 里的
`ollama` + `bge-m3`。

我做的事：把 `.env` 里那行判成"历史实验残留"，换成进程内 384 维
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`；然后顺着这个错误往下改
——`config.py` 默认值、`conftest` 注释、`Dockerfile`、`start.sh`、文档里的分数，全部
对齐到新配置，还提交了 commit。那一轮所有对外数字都是这套配置测出来的。

为什么这是错的：

1. **成因是服务没起，不是配置写错。** 正确动作只有一个：`ollama serve`（早已授权）。
   我修的是一个不存在的 bug。
2. **`bge-m3` 不是实验参数，是产品组件。** 换它等于把被测对象换掉再测，测出来的不是
   产品的数字，是另一台机器的数字。
3. **它沿一条链扩散。** 从 `.env` 到默认值到部署脚本到文档，每改一处都让"原配置是什么"
   更难还原；后来要复原，得一处一处往回找。
4. **动机是"让流程先跑通"。** 和第一条事故是同一个动作：把外部条件改成能通过的样子，
   而不是承认并修复当前状态。
5. **它还会长出假结论。** 拿错配置的数字去解释技术现象（"小模型差 8 个点"），读起来
   像实验结论，实际是测量误差。测量口径错了，后面所有解释都不可信。

处置：`.env` 与 `config.py` 默认值恢复 `ollama` + `bge-m3`；加了四处防再犯
（`settings_for()` 只认显式传入、AST 测试禁止评测脚本写死模型名、`Settings` 校验提示、
`start.sh` 只提示不改配置）。

**这一轮没有被记成一版口径，也不该被记成。** 它的分数不进[检索口径沿革](retrieval-history.md)
的版本表，不给版本号，不在任何地方作为"小模型性能"或"某一版结果"引用。把它写成
"v5 首版"，等于替它发一张合格证。

## 两次事故是同一个动作

看起来一次在数据、一次在环境，机制完全一样：**遇到障碍时，改的是让结果好看的那个变量，
而不是障碍本身。** 第一次的障碍是"结论撑不住"，第二次的障碍是"服务没起来"。两次都
有一个当时就能做、只是更麻烦的正确动作：改写那句话 / 启动那个服务。

这也是为什么它们不能混进"调试记录"：调试是在既有约束下把东西弄对；这两次是把约束
本身改掉了。

## 判定规则：改语料、改标注、改计分口径之前，先做四次自问

1. **反向检验。** 如果这个结论反过来，我还会做同样的改动吗？如果不会，那就是操纵。
2. **依据来源。** 改动的理由必须能指向材料自身的客观属性——页数、文字层有没有、
   时长、字幕有没有、区间是否跨块。指向"某个数字会变好看"或"某个旧说法会成立"的，
   一律不成立。
3. **零贡献检验。** 这个改动会让指标变化吗？如果不会，那它是为了什么？只可能为了
   叙事。（这条是第一次事故最锋利的探针。）
4. **分母纪律。** 把题标成不计分，必须有材料层面的客观理由，**并且**写明谁来接管它
   （哪个能力用例覆盖）。不允许难题靠"不计分"消失。

## 改组件、改默认值之前：先分清是哪一类改动

- **环境没起来 → 起环境。** 启动服务、拉模型、装扩展是日常操作，不需要额外批准，
  更不许用"换个组件"绕过去。
- **可以直接改**：脚本 bug、文档里的错数、测试、新增工具。
- **必须先问**：默认值、依赖、部署方式（`Dockerfile`、compose、`start.sh`、`.env`）。
  这些是产品的形状，不是我的实验参数。
- **指标必须带口径标签**：模型名、语料版本、可评分数。没有标签的分数不许写进文档。

## 什么算正常调整，什么算迎合结论

正常调整：

- 材料客观属性标错了（页数错、字幕段数错、标注区间跨块）——修，并记录修的依据。
- 标注过窄或过宽——复核后按证据改，改完在文档里写清为什么；不许只挑对自己有利的题改。
- 研究问题变大导致语料扩张（如 17 题 → 83 题）——允许，但必须在换之前就声明
  "旧数字作废、不可比"，而不是换完再解释。历次口径与旧数字统一记在[检索口径沿革](retrieval-history.md)。
- 换向量模型、换精排模型——允许，那是有对照、有新基线的一次口径变更；与"因为服务
  没起来临时换掉产品组件"是两件事，前者进沿革表，后者进这份文件。

迎合结论（禁止）：

- 为保住某个结论增删材料。
- 只对被质疑的那几题放宽标注（选择性放宽）。
- 改分母让比例好看。
- 用"样本小"当挡箭牌，回避本来能做的大样本复核。

## 披露义务

- 任何语料、标注、计分口径的改动，commit message 写动机与依据，别只写"更新数据"。
- 换组件、改默认值、改部署方式同样要写动机，并且写清"这是谁的决定"。
- 新旧结果不可比时，在文档里明写"旧数字作废"，不要并列摆放让人误读。
- 结论变差时，顺序是先记录、再分析、最后才谈改进；顺序不许倒过来。

## 机器能挡住的那一小部分

`scripts/check_evaluation.py`（CI 里跑，不调模型）会拒绝：

- 检索集里标了 `unretrievable` 却没写 `reason` 或 `readable_by` 的题——不许有无人
  接管的豁免；
- `reason` 里出现意图性表述（"为了让"、"使…成立"、"结论成立"之类）——把最脏的那种
  写法挡在提交前。

`tests/test_eval_scripts.py` 挡住另一头：会产出评测数字的脚本不许写死向量模型或来源，
只能走 `config.py` 默认值或显式命令行参数——想换模型就必须在命令里留下痕迹。

剩下的挡不住，只能靠上面几次自问。
