# 跨材料检索方案（待决策，未改代码）

更新于：2026-11-24。这份文档只回答一件事：**4 道跨讲对照题为什么 0/4，要救回来需要付什么代价。**
除这份文档外没有任何代码改动；下面每条都标了"改什么 / 预估收益 / 代价 / 风险"。

## 一、现状（bge-m3 + 精排，池深 120）

| 题 | 目标材料与区间 | 候选池里的位置 |
|---|---|---|
| cross_serve_cost | cs9 [4462,4505] | 第 5 ✓ |
| | cs10 [2539,2579] | **未进池**（cs10 只进 2 条） |
| cross_flash_kv | hy_flash [873,916] | **未进池**（进池 15 条，都不覆盖） |
| | hy_kv [181,224] | **未进池**（进池 11 条） |
| cross_long_context | cs4 [2022,2066] | 第 35 |
| | hy_kv [1059,1103] | 第 4 ✓ |
| cross_kv_reduce | hy_kv [1410,1452] | 第 11 |
| | cs10 [3840,3884] | 第 31 |

`all` 模式要求两份证据同时进前 5，所以只要有一份缺席就是 0 分。

## 二、根因：不是"被别的材料挤掉"，是双塔分不清这些语义

把每份材料**单独**排序（`scripts/inspect_within_material.py`），看目标块在它自己那份材料里排第几：

| 目标 | 材料规模 | 材料内名次（BM25+向量融合） |
|---|---|---|
| cs9 | 108 块 | **1** |
| cs4 | 122 块 | **4** |
| hy_kv（长上下文那题） | 53 块 | 12 |
| hy_kv（剪枝那题） | 53 块 | 12 |
| cs10（服务瓶颈） | 123 块 | 16 |
| hy_kv（Flash 对照那题） | 53 块 | 19 |
| cs10（减 KV 做法） | 123 块 | 26 |
| hy_flash | 69 块 | **67** |

结论有两条，都直接影响方案选择：

1. **"前 5 被同一材料占满"不是原因。** 上、下文已实测：给每份材料限 3 条，指标从 0.631 掉到 0.583，
   跨讲仍 0/4。位置空出来了，缺的证据还是找不到。
2. **瓶颈是单塔向量对"这段在讲什么"的区分度。** 最极端的是 hy_flash 那块：原文通篇在讲
   "工作台上不能放跟长度 L 有关的东西"，**全块没有出现 "Flash Attention" 这个词**，所以
   BM25 得 0 分、向量排 67/69。而问题问的是"Flash Attention 省的是哪类开销"——
   要命中它，模型必须知道"不把跟 L 有关的东西放片上"就是 Flash Attention 的 IO 省法。

由此可以算出**按材料召回的天花板**（每份材料各取前 k 条，再交给精排）：

| 每材料取前 k | 目标进池数（8 个） | 两证据齐全的题（4 题） |
|---|---|---|
| 10 | 2 | 0/4 |
| 20 | 5 | 2/4 |
| 30 | 6 | **3/4** |
| 70 | 8 | 4/4 |

也就是说：**即使每材料取 30 条，也只能让 3 道题的两份证据都进池**，而最终还要靠精排把
它们排进前 5——精排对这两条的排序能力尚未验证。

## 三、四条可选路径

### 方案 A：扩大精排候选池（改动最小）

- **改什么**：`rerank_candidates` 从 20 提到 100 左右，`search` 的候选深度同步加深。
- **收益**：已经能看到一部分——池深 120 + 精排 100 时 `cross_kv_reduce` 的 hy_kv 升到第 11、
  `cross_long_context` 的 hy_kv 到第 4。但 cs10、hy_flash、hy_kv[181,224] 仍在池外，
  所以**预计跨讲仍 0/4 或 1/4**。
- **代价**：单次提问从约 0.9 秒涨到 4–5 秒（100 对逐对推理，CPU）。
- **风险**：低。但很可能白付延迟。
- **判断**：单独做不解决根因，只作为其它方案的一部分。

### 方案 B：分材料召回 + 精排（最对症）

- **改什么**：`search` 增加一个"分面召回"模式——对每份材料各取前 k 条（k≈20–30），
  合并后交给精排重排；是否启用由查询是否像"跨材料问题"决定（见下）。
- **收益**：按上表，k=30 时 3/4 道题的两份证据都能进池，剩下的是精排能不能把它们排进前 5。
  **这个"精排能不能"必须实测**——一次离线跑（4 题 × 330 候选）约 2 分钟就能给出答案，
  不需要改产品代码。
- **代价**：11 份材料 × 30 = 330 个候选逐对推理，约 15 秒/次；即使只挑 2–3 份相关材料，
  也要 90 个候选、约 4 秒。
- **风险**：中。**对所有单材料问题是负收益**——候选池被别的材料的块稀释，精排排序键不稳时
  会把正确答案挤下去。所以必须**门控**，不能默认全开。
- **门控怎么做**：查询里出现"两讲 / 对比 / 各自 / 分别"或明确点出两个来源（第九讲、第十讲）时
  才走分面召回。这个判断用规则就能做，不必调模型。

### 方案 C：换更强的向量模型

- **改什么**：`LA_EMBEDDING_MODEL` 换成 1024–1536 维的更强多语言模型（候选：
  `Qwen/Qwen3-Embedding-0.6B` 2.38 GB、`jinaai/jina-embeddings-v3` 2.29 GB，走 fastembed 的
  `local` 或 ollama 拉取）。
- **收益**：bge-m3 已经把整体从 0.554 拉到 0.639（+8.5pt），说明模型能力是这条链路的主变量；
  更强的模型有希望把 hy_flash 那块从 67 名往前挪。**但没有任何先验保证**，必须实测。
- **代价**：下载 1.1–2.4 GB（本机实测 HF 直连 90–170 KB/s、镜像 650 KB/s，约 30–60 分钟）；
  单次查询向量化时间与内存都会上升。
- **风险**：中。可能在单材料题上涨、在另一些题上退；换模型后所有数字要重新标定一次。
- **判断**：值得试，但应排在 B 之后——B 是结构问题，C 是模型上限问题，两者正交。

### 方案 D：改分块（句对齐 + 重叠）

- **改什么**：视频块目前是"≤45 秒、句中断开"（`video_sliding_window` 那条就是定义句被切两半）。
  改成分句边界对齐、相邻块重叠 1–2 句。
- **收益**：直接改善"块内没有查询词"的情况——hy_flash 那块开头就是半句"一次都放到工作台上"，
  加上前一句会更可检索。对单材料题也可能有普适收益。
- **代价**：**整库重分块 + 重新嵌入 942 块**，全部指标重置；需要复核 92 道题的标注区间是否仍被
  单个块完整覆盖（当前 65 个时间区间全部被覆盖，改分块后要重新验证）。
- **风险**：高。它同时改了语料和指标口径，容易又变成"数字不可比"。**只有在 A/B/C 都试过
  仍不够时才考虑**，而且要先把"覆盖率复核"写成脚本。

## 四、建议的执行顺序

1. **先做零改动的验证**（约 5 分钟，不碰产品代码）：写一个一次性脚本，用方案 B 的候选池
   （每材料取前 30）过一遍精排，看 4 道题能不能进前 5。**这决定了 B 值不值得做。**
2. 若上一步 ≥2/4：实现方案 B + 门控，用同一套评测确认单材料题不退化（目标：总 Hit@5 不明显下降）。
3. 若上一步 <2/4：说明精排也认不出这些块，转方案 C 换模型，用同样的 4 题 + 全量 83 题复测。
4. 方案 D 留作最后手段。

## 五、明确不做的三件事

1. **不放宽 `targets_mode=all` 到 any。** 那等于把"跨材料对照"这道能力题删掉。
2. **不允许"相邻块算命中"。** `cross_kv_reduce` 有一块紧贴目标区间（差 1 秒），但那条讲的是
   attention sink，不是 KV cache 剪枝——算命中就是用错的证据蒙对。
3. **不改标注区间去迁就检索结果。** 65 个时间区间全部能被单个块完整覆盖，说明标注本身是可达的，
   问题在检索侧。

## 六、需要你决定的事

- 方案 B 的延迟（门控后约 4 秒/次）可以接受吗？如果不行，B 就只能做成"显式开关"（用户点"跨材料对照"才开）。
- 方案 C 允许下载 1.1–2.4 GB 模型吗？允许的话我按第 1–3 步顺序跑。
